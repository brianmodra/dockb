# API Design: Frontend ↔ Backend

## Core Principle

**Semantic events, not text diffs.** The FE tells the BE *what* changed relative to the hierarchy, as opposed to what character offset it occurred at.
Mapping between character positions and model elements is maintained by ProseMirror's tree resolution on both sides — no fragile position-mapping code
in either frontend or backend.

Tokens are **server-only** — computed by `SentenceTokenizer`/spaCy, stored in Neo4j, and never transmitted over the wire.

---

## Wire Format

### ProseMirror JSON (Chapter, Paragraph, Sentence)

Every node in ProseMirror's JSON format has exactly this shape:
```json
{
  "type": "...",
  "attrs": { ... },
  "content": [ ... ]
}
```

Chapter, Paragraph, and Sentence are transmitted as ProseMirror JSON trees.
Individual GET requests return the **full tree** from the requested node downward.

Chapter GET-by-id responses are **not paginated**. The FE needs the entire
chapter tree in memory to use ProseMirror's `resolve(pos)` for position-to-node
mapping — partial responses would break that contract and add complexity for no
benefit. Very large chapters (e.g. >100k sentences) will eventually hit gateway
limits and fail; this is an accepted design limitation.

To mitigate this, all API responses support **gzip compression** (the client
sends `Accept-Encoding: gzip` and the server compresses the response body
automatically). This substantially reduces transfer size and delays the point
at which gateway limits are reached, but does not remove the ceiling entirely.

E.g. `GET /api/chapters/{id}`:
```json
{
  "type": "chapter",
  "attrs": { "id": "ch-uuid", "title": "Introduction" },
  "content": [
    {
      "type": "paragraph",
      "attrs": { "id": "p-uuid" },
      "content": [
        {
          "type": "sentence",
          "attrs": { "id": "s-uuid" },
          "content": [
            { "type": "text", "text": "Hello world." }
          ]
        }
      ]
    }
  ]
}
```

`GET /api/paragraphs/{id}` returns a paragraph node with its full sentence tree.
`GET /api/sentences/{id}` returns a sentence node with its text content.

### Document (plain JSON)

A Document is **not** a ProseMirror node. It is a plain JSON object with `attrs`
and a flat list of chapter summaries (attrs only, no child content):

`GET /api/documents/{id}`:
```json
{
  "attrs": { "id": "doc-uuid", "title": "Forgiveness", "author": "Wes Almond" },
  "chapter_summaries": [
    { "id": "ch-uuid-1", "title": "Chapter 1" }
  ]
}
```

The FE loads a chapter via `GET /api/chapters/{id}` to get its full tree.

### Schema

```
document: { attrs: { id: string, title: string, author: string }, chapter_summaries: chapter_summary* }
chapter_summary: { id: string, title: string }
chapter:   { content: "paragraph+", attrs: { id: string, title: string } }
paragraph: { content: "sentence+",  attrs: { id: string } }
sentence:  { content: "text*",      attrs: { id: string } }
text:      { inline: true,          attrs: {} }
```

Note: attrs in this codebase at the point of typing up this spec file are simple. Obviously
there will be more than title, author, and other content, such as a premise, an elevator pitch, etc.
Chapter, Sentence, and Text will also have formatting attributes. The text object does not even have attrs yet,
but in future it most likely will.

The API is therefore incomplete, and will be added to later. It should not be implemented with hard
limitations and short-sighted assumptions which would make it difficult to extend later on.

### ID Convention

All node IDs are UUIDs (v4) generated by the creator. Since UUIDs are globally unique, the FE or BE
can generate IDs for new nodes without conflict. No temporary-ID mapping is needed.

Note that in the examples in this document, more man-readable ID strings are used to make it easier to illustrate,
but in reality, all IDs will be UUIDs.

## REST Endpoints

A "summary" response (returned by list endpoints) lists the attrs of model objects, not their content.
Individual GET-by-id endpoints return the full ProseMirror tree from the requested node downward.

## REST responses

**GET** responses return the requested data directly (no envelope).

**POST** / **PUT** / **DELETE** responses are wrapped in a status envelope:

```
response:  { status: status, notifications?: notification+ }
status:    { code: string, message: string }
notification: { type: string, ... }
```

See **Async Notifications** for notification payload definitions.

A non-error response will have code `"ok"` and message `"success"` and a 2xx HTTP status code.

### Document CRUD

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/documents` | List summaries |
| `POST` | `/api/documents` | Create document from the supplied data (See **POST Document Data**) |
| `GET` | `/api/documents/{id}` | Returns the document attrs and chapter summaries (plain JSON — see **Wire Format**) |
| `PUT` | `/api/documents/{id}` | Replace only the document attributes (title, author — see **PUT Document Data**). Chapters and their content are not affected |
| `DELETE` | `/api/documents/{id}` | Delete doc + all children |

#### POST Document Data

Note that the POST document endpoint does not allow you to supply the paragraphs of the document,
it creates an empty document with the supplied attributes.
The body of a POST method to the /api/document endpoint will conform to the following schema:

```
document: { attrs: { id: string, title: string, author: string }, relations?: { after_document_id: string } }
```

E.g. (no ordering — this is the first document):
``` json
{
  "attrs": { "id": "d-uuid-1", "title": "Faith", "author": "Sha'ul ha-Tarsi" }
}
```
Or, to add after an existing document:
``` json
{
  "attrs": { "id": "d-uuid-2", "title": "Hope", "author": "Paulos Tarseus" },
  "relations": {
    "after_document_id": "d-uuid-1"
  }
}
```

Note that the ID is passed in from the FE, not generated in the BE.

#### PUT Document Data

The body of a PUT method to the /api/document endpoint will conform to the following schema:

```
document: { attrs: { id?: string, title: string, author: string } }
```
When using PUT, the ID is supplied in the URL, so is optional in the body of the PUT,
but must be exactly the same if included.

E.g.
``` json
{
  "attrs": { "title": "Love", "author": "Yōḥānān ha-Shaliaḥ" }
}
```

### Paragraph CRUD

Note that the GET list of paragraphs is filtered by chapter_id.

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/paragraphs?chapter={id}` | List summaries |
| `POST` | `/api/paragraphs` | Create paragraph from the supplied data (See **POST Paragraph Data**) |
| `GET` | `/api/paragraphs/{id}` | Returns the full paragraph as a ProseMirror JSON tree (sentences → text) |
| `PUT` | `/api/paragraphs/{id}` | Full replacement from the supplied data (See **PUT Paragraph Data**) |
| `DELETE` | `/api/paragraphs/{id}` | Delete paragraph + all children |

#### POST Paragraph Data

The body of a POST method to the /api/paragraph endpoint will conform to the following schema:

```
paragraph: { attrs: { id: string }, content: "sentence+", relations: { chapter_id: string, after_paragraph_id?: string } }
sentence:  { content: "text*", attrs: { id: string } }
text:      { inline: true }
```

E.g.
``` json
{
  "attrs": { "id": "p-uuid-1" },
  "content": [
    {
      "type": "sentence",
      "attrs": { "id": "s-uuid-1" },
      "content": [
        { "type": "text", "text": "Hello world." }
      ]
    }
  ],
  "relations": {
    "chapter_id": "c-uuid-1"
  }
}
```
Or, to add after an existing paragraph:
``` json
{
  "attrs": { "id": "p-uuid-2" },
  "content": [
    {
      "type": "sentence",
      "attrs": { "id": "s-uuid-2" },
      "content": [
        { "type": "text", "text": "Hello Mars." }
      ]
    }
  ],
  "relations": {
    "chapter_id": "c-uuid-1",
	"after_paragraph_id": "p-uuid-1"
  }
}
```

#### PUT Paragraph Data

The body of a PUT method to the /api/paragraph endpoint will conform to the following schema:

```
paragraph: { attrs: { id?: string }, content: "sentence+", relations?: { chapter_id?: string, after_paragraph_id?: string } }
sentence:  { content: "text*", attrs: { id: string } }
text:      { inline: true }
```

The id is optional, but if it is included, it must match the id used in the URL.
The `relations` block is optional. If omitted, the paragraph stays in its current
chapter and position. If `chapter_id` is provided, the paragraph is re-parented to that
chapter. If `after_paragraph_id` is also provided, it is inserted after the specified sibling
within the target chapter.

E.g.
``` json
{
  "attrs": {},
  "content": [
    {
      "type": "sentence",
      "attrs": { "id": "s-uuid-1" },
      "content": [
        { "type": "text", "text": "Hello world." }
      ]
    }
  ]
}
```

**Re-parenting and sentence life cycle:** When a sentence ID that was a child of
this paragraph is absent from the PUT body, the sentence is **unlinked** from the
paragraph (its parent is set to `None`) but is **not deleted**. True deletion
only happens via `DELETE /api/sentences/{id}`. This allows the FE to move a
sentence between paragraphs by first calling `PUT /api/sentences/{id}` with a
`relations.paragraph_id` pointing to the target paragraph (see **PUT Sentence
Data**), then PUTting the source paragraph without that sentence — the sentence
is re-parented rather than destroyed.

#### POST or PUT Paragraph data response

The POST or PUT returns immediately after the paragraph is saved. If NLP processing
detects sentence or paragraph splits, the changes are delivered asynchronously via
notifications (see **Async Notifications**).

**Sentence split** — a single sentence in the paragraph body was found to contain
multiple sentences after spaCy processing. Payload shape:

```
notification: { type: "sentence_split", paragraph_id: string, changed_sentences: "sentence+" }
sentence:     { content: "text*", attrs: { id: string } }
text:         { inline: true }
```

E.g.
``` json
{
  "type": "sentence_split",
  "paragraph_id": "p-uuid-1",
  "changed_sentences": [
    {
      "content": [
        { "type": "text", "text": "The quick brown fox jumps over the lazy dog." }
      ],
      "attrs": { "id": "s1" }
    },
    {
      "content": [
        { "type": "text", "text": " " },
        { "type": "text", "text": "Additional text." }
      ],
      "attrs": { "id": "s2" }
    }
  ]
}
```

**Paragraph split** — the combined text across sentences was found to contain
paragraph boundaries. Payload shape:

```
notification: { type: "paragraph_split", chapter_id: string, changed_paragraphs: "paragraph+" }
paragraph:    { content: "sentence+", attrs: { id: string } }
sentence:     { content: "text*", attrs: { id: string } }
text:         { inline: true }
```

Note that it is possible for a paragraph split to also include sentences that were split.

#### PUT Sentence Data

The body of a PUT method to the /api/sentence endpoint will conform to the following schema:

```
sentence:  { attrs: { id?: string }, content: "text+", relations?: { paragraph_id?: string, after_sentence_id?: string } }
text:      { inline: true }
```

The id is optional, but if includede, must match teh id in the URL.

The `relations` block is optional. If omitted, the sentence stays in its current
paragraph and position. If `paragraph_id` is provided, the sentence is re-parented to that
paragraph. If `after_sentence_id` is also provided, it is inserted after the specified sibling
within the target paragraph.

E.g. (update content only):
``` json

  "attrs": {},
  "content": [
    { "type": "text", "text": "First sentence." }
  ]
}
```

E.g. (update content and reparent):
``` json
{
  "attrs": {},
  "content": [
    { "type": "text", "text": "First sentence." }
  ],
  "relations": {
    "paragraph_id": "p-uuid-2",
    "after_sentence_id": "s-uuid-3"
  }

```

The POST or PUT returns immediately after the sentence is saved. If NLP processing
detects a sentence split, the changes are delivered asynchronously via notifications
(see **Async Notifications**). The payload shape:

```
notification: { type: "sentence_split", paragraph_id: string, changed_sentences: "sentence+" }
sentence:     { content: "text*", attrs: { id: string } }
text:         { inline: true }
```

See the **POST or PUT Paragraph data response** section for an example.

### History API

| Method | Path | Purpose |
|---|---|---|
| `GET`  | `/api/history/{chapter_id}?limit={limit}&offset={offset}` | Get change history list |
| `PATCH` | `/api/history/{chapter_id}` | restore the particular version of the chapter by commit ID |

The snapshot file is rewritten before every chapter edit; see
[`src/dockb/infrastructure/history/README.md`](../infrastructure/history/README.md)
for details.

Syntax of the response payload of a GET history list request:
```
history: snapshot*
snapshot: { datetime: string, commit_id: string } 
```

Syntax of the payload of a PATCH history commit request will be:
```
commit: {commit_id}
```

The back end will read the snapshot file as it was at that commit, and re-hydrate the neo4j database, and
return the full chapter data as a ProseMirror JSON tree (paragraphs → sentences → text) in exactly the
same format as a 
`GET /api/chapters/{id}` would return it.

#### Paging

The GET history request will support paging using the typical format of limit and offset, e.g.
| Method | Path |
|---|---|
`GET`  | `/api/history/{chapter_id}?limit=20&offset=40`

#### Order of return

The history is returned in reverse chronological order: most recent first.

### Batch typing (FE coalesces rapid keystrokes)

The FE will not send all keystrokes, that would be an excess of I/O. It uses a debounce
timer, coalesces rapid keystrokes, and returns a single POST or PUT.

### Async Notifications

NLP processing (sentence splitting, paragraph splitting) runs asynchronously after a
POST or PUT returns. When processing completes, the results are stored in the session
context and delivered to the FE via two mechanisms:

**Piggy-back.** Any subsequent `POST`/`PUT`/`DELETE` response includes a `notifications`
array if there are pending notifications. Once delivered, notifications are cleared from
the queue and will not be repeated.

**Poll.** The FE can explicitly fetch pending notifications:

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/notifications` | Returns all pending notifications and clears the queue |

Returns an empty `notifications` array if the queue has nothing pending (no blocking), e.g.:

```json
{
  "notifications": [
    {
      "type": "sentence_split",
      "paragraph_id": "p-uuid-1",
      "changed_sentences": [...]
    }
  ]
}
```

#### Delivery scenarios

| Scenario | How the FE receives the notification |
|---|---|
| User typing rapidly | Piggy-back on next PUT request |
| User pauses briefly | Poll (`GET /api/notifications`) catches it within the poll interval |
| User closes and reopens chapter | `GET /api/chapters/{id}` returns current tree — no notification needed |
| Long idle | Poll delivers within the poll interval |

#### Notification types

| Type | Payload | Trigger |
|---|---|---|
| `sentence_split` | `{ paragraph_id, changed_sentences }` | spaCy detects multiple sentences in a sentence's text |
| `paragraph_split` | `{ chapter_id, changed_paragraphs }` | spaCy detects paragraph boundaries in combined text (bulk import only) |

Note that a paragraph split can include sentence splits, and a sentence operation could cause a paragraph split.

## Error Responses

An error response is indicated by the status.code not being "ok".

```json
{
  "status": {
    "code": "sentence_not_found",
    "message": "No sentence with id 's-999' exists in document 'd-1'."
  }
}
```
Following is a non-exhaustive illustrative list of error responses and HTTP codes.

| Code | HTTP Status | Meaning |
|---|---|---|
| `document_not_found` | 404 | Document ID does not exist |
| `sentence_not_found` | 404 | Sentence ID does not exist in this document |
| `paragraph_not_found` | 404 | Paragraph ID does not exist in this document |
| `chapter_not_found` | 404 | Chapter ID does not exist in this document |
| `invalid_payload` | 422 | JSON body does not match expected schema |
| `processing_error` | 500 | spaCy/hydration/internal failure |
| `conflict` | 409 | Document version mismatch (optimistic locking) |
